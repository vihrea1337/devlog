## Структура репозитория
- `backend/` — сервер Ktor (самостоятельный Gradle-проект).
- `androidApp/` — Android-приложение (самостоятельный Gradle-проект).
- `shared/` — **общий модуль с DTO**: один контракт API на бэкенд и Android,
  подключается обоим через `includeBuild("../shared")`. Меняешь поле — меняй здесь,
  оба проекта увидят это на компиляции. Тесты: `./gradlew :shared:test` из `backend/`.
- `deploy/server/` — файлы деплоя и runbook, `docs/` — проектные документы.

## Стек (зафиксирован)
- **Бэкенд:** Kotlin + Ktor + PostgreSQL + Exposed + HikariCP.
- **Схема БД:** миграции Flyway (`backend/src/main/resources/db/migration/V…__.sql`).
  Новая колонка = правка `Tables.kt` **и** новый файл миграции; совпадение стережёт
  тест `SchemaMigrationTest`. Подробности — `docs/data-model.md`.
- **ИИ:** Groq (OpenAI-совместимый API, бесплатно), модель `openai/gpt-oss-120b` (с 2026-10-10; 20b путала факты). Ключ только
  на сервере (`backend/secrets.properties` → `groq.api.key`, в .gitignore), обработка в фоне.
  _(Изначально планировался Claude API — заменён на Groq ради бесплатности на старте.)_
- **Клиенты:** Kotlin Multiplatform + Compose Multiplatform (Android/iOS/Desktop из общего кода).
  Веб на старте — HTML-страница, которую отдаёт сам бэкенд.
- **Авторизация:** JWT, пароли хешируются, изоляция пользователей (multi-tenant) с Фазы 1.
- **Деплой:** Docker на общем сервере в `/opt/devlog`, HTTPS через Caddy + DuckDNS на порту 34444
  (80/443 заняты Solmu), по образцу Expenses. Runbook — `deploy/server/README.md`.

## Что сделано без участия пользователя (2026-09-02)
Офлайн-кэш ленты в Android поверх готового `since`-протокола (пункт 2 из плана ниже),
в два захода:

1. **Чтение офлайн**: в `shared/` появились Ktor Client (движок CIO) и SQLDelight
   (`db/Entries.sq`), `EntryRepository` в `sync/` тянет изменения с `/api/entries/changes`
   и кладёт их в локальную базу, `FeedViewModel` в androidApp читает ленту из кэша
   (работает без сети), а не гоняет Retrofit при каждом открытии экрана.
2. **Запись офлайн**: `addEntry`/`deleteEntry` тоже переведены на офлайн-первый путь —
   пишут сразу в локальный кэш и в очередь `pendingOperation` (`db/PendingOperations.sq`),
   `sync()` сначала отправляет очередь (с повтором и экспоненциальной задержкой при
   сбое), потом тянет изменения. При самостоятельном ревью найдена и закрыта гонка:
   удаление записи ровно в момент, когда её создание ещё летит по сети, могло привести
   к тому, что запись "воскресала" после ответа сервера — теперь такое исключено
   (подробности и trade-off — в `docs/roadmap.md`, Фаза 3.7).

Прогнано после каждого из двух заходов: `./gradlew :shared:test` (контракт +
`EntryRepositorySyncTest` + `EntryRepositoryPendingQueueTest`, 17 тестов суммарно) и
`androidApp :app:assembleDebug` — всё зелёное. **На реальном телефоне не проверялось.**

3. **Импорт текстового лога (в т.ч. выгрузок Claude Code)** — по образцу уже готового
   импорта GitHub. У сессий Claude Code нет стабильного публичного формата экспорта,
   поэтому вместо разбора конкретного JSONL сделан **общий импорт**: `POST
   /api/import/text {text, projectId?}` режет вставленный текст на дни по датам
   ГГГГ-ММ-ДД в строках, один день — одна запись (дальше её разбирает тот же ИИ-воркер).
   Панель добавлена на веб-страницу рядом с GitHub-импортом (Android UI, как и у
   GitHub, пока нет). Дедуп — по дню и содержимому (не только по дню, как у GitHub):
   тот же текст повторно не дублирует записи, а другой лог за тот же день ложится
   отдельно. Полное обоснование выбора формата — `docs/architecture.md`.
   Тесты: `TextImportTest` (9, backend). Проверено и вручную сквозным HTTP-запросом
   к реально запущенному локальному серверу (не только юнит-тесты). **Не проверено:**
   реальная выгрузка настоящей сессии Claude Code (только синтетические примеры),
   UI не открывался в браузере руками.

4. **Флак `SyncTest` — найдена и исправлена настоящая причина** (не гонка в тесте, а
   реальный баг в проде): курсор `/api/entries/changes` был завязан на `updated_at`
   (timestamp) — сначала голое «`> since`», потом составной `(updated_at, id)`. Оба
   варианта ломались, если несколько записей получали ОДИНАКОВЫЙ `updated_at` (легко
   при быстром создании подряд — ровно то, что делает импорт в цикле): без тай-брейка
   запись терялась навсегда между страницами; с тай-брейком по случайному `id` могла
   потеряться уже НОВАЯ запись, если её UUID оказался "меньше" id записи-курсора —
   случайный порядок UUID не связан с порядком вставки. **Фикс**: `Entries.syncSeq`
   (новая колонка `sync_seq`, `V6__entries_sync_seq.sql`) — значение из настоящей
   БД-последовательности (`entries_sync_seq`), строго монотонное, без исключений.
   Курсор `since`/`serverTime` теперь — этот счётчик, а не время. Все 9 точек записи
   в `Entries` (create/update/delete/setStatus/AI-очередь) теперь ставят его при каждом
   изменении. Добавлен детерминированный регрессионный тест (форсирует совпадение
   `updated_at` напрямую через БД — не полагается на удачу с таймингом, как раньше) —
   прогнан 10 раз подряд в цикле, 10/10 зелёных, плюс 3 раза подряд весь тестовый набор.
5. **Приватные репозитории GitHub** — токен пользователя (per-user, зашифрован
   AES-GCM в отдельной таблице `github_integrations`, ключ — из JWT_SECRET, не
   логируется и не возвращается в API-ответах — только факт привязки). Панель на
   веб-странице обновлена. **Проверено вживую** через `gh auth token`: подтверждено,
   что приватный репозиторий (`graywilson/moimatch`) реально виден только с токеном,
   и что неверный токен корректно отклоняется (502, не тихий фолбэк на публичный доступ).
   ⚠️ **При этой же проверке найден отдельный, более серьёзный баг, НЕ связанный с
   приватными репозиториями**: у реальных GitHub `PushEvent` больше нет поля
   `payload.commits` (только `before`/`head` SHA) — наш парсер эту форму не понимает
   и распознаёт 0 коммитов из 37 реальных пушей. Это ломает импорт GitHub **целиком**,
   включая уже помеченную "готовой" публичную часть от 12.08 — юнит-тесты зелёные
   только потому, что фикстура в `GithubImportTest.kt` использует устаревшую форму
   ответа. **Починено 2026-09-03** (см. пункт 6 ниже) — на момент этой записи ещё
   было открыто, оставлено как есть для истории находки.
   **Живая проверка 2026-09-04:** пользователь подтвердил на реальном локальном сервере —
   импорт под `vihrea1337` подтянул реальный коммит недельной давности с верной датой.
6. **Починен баг `payload.commits`** (2026-09-03): для каждого пуша теперь ходим
   дополнительно на GitHub Compare API (`/repos/{repo}/compare/{before}...{head}`) за
   настоящими сообщениями коммитов, с лимитом догрузок (15 без токена / 150 с токеном)
   и остановкой по rate-limit GitHub без потери уже собранного (`ImportResult.truncated`).
   Подробности — `docs/roadmap.md`, Фаза 4.
7. **Офлайн-редактирование текста записи + настоящий last-write-wins** (2026-09-03):
   `EntryRepository.enqueueUpdate()` — та же схема, что у create/delete из пункта 2: правка
   сразу видна в ленте, `PUT /api/entries/{id}` уходит в очередь и уезжает при ближайшем
   `sync()`. В androidApp впервые появилась сама возможность править текст записи (кнопка
   «Править» на карточке — раньше такого не было даже онлайн, только на вебе). Конфликт с
   сервером (ИИ успел переобработать запись раньше нашей отправки, или её же поменяли с
   другого устройства) разрешается по `updatedAt`: более свежая версия побеждает, устаревшая
   правка выкидывается из очереди, если проиграла. Самостоятельное ревью нашло и закрыло
   реальный баг: повторная правка текста, пока предыдущая уже в полёте, теряла бы вторую
   правку насовсем (не на секунду) — исправлено тем же приёмом, что уже был у create
   (`inFlightUpdateEntryIds`). Подробности, все trade-off'ы и полный список тестов —
   `docs/roadmap.md`, Фаза 3. Тесты: `./gradlew :shared:test` (+10) и
   `androidApp :app:assembleDebug` — зелёное. **Не проверено вживую на телефоне.**

8. **Экспорт отчёта в GitHub** (2026-09-03) — обратная сторона импорта коммитов: кнопка
   «Экспортировать в GitHub» на готовом отчёте (`POST /api/reports/{id}/export-github`)
   кладёт его в один changelog-файл (по умолчанию `docs/devlog.md`) в репозитории проекта
   через GitHub Contents API — рядом с настоящими коммитами появляется человеческий текст
   "что и зачем делалось". Настройка репозитория/пути — в панели проекта
   (`github_export_repo`/`github_export_path`, миграция V7). **Сознательно ручное действие,
   не автоматика** — писать в чужую историю коммитов молча в фоне было бы слишком навязчиво.
   Повторный экспорт того же отчёта обновляет его раздел на месте (метка —
   HTML-комментарий `<!-- devlog:report:{id} -->`), не дублирует; новые разделы — сверху.
   Тесты: `GithubExporterTest` (6, чистая сборка файла) + `ReportExportGithubTest` (8, HTTP
   с замоканной сетью) — все зелёные, бэкенд теперь 136 тестов. Подробности, дизайн-решения
   и известные компромиссы — `docs/roadmap.md`, Фаза 4.
   **Живая проверка 2026-09-04:** пользователь запустил экспорт на реальном локальном
   сервере против `vihrea1337/devlog` — коммит `devlog: ... (period)` появился в файле
   `docs/devlog.md` на ветке по умолчанию, содержимое и маркер раздела в порядке.

9. **Импорт коммитов с GitLab** (2026-09-03) — второй провайдер импорта, НЕ копия GitHub-кода
   с заменой имён: реальный API GitLab устроен иначе, и `GitlabImport.kt` это отражает
   (полное обоснование в докстринге файла и `docs/roadmap.md`, Фаза 4). Главные отличия:
   токен ОБЯЗАТЕЛЕН (у GitLab нет анонимного режима — значит, нет и отдельного поля "логин
   GitLab" в профиле, `GET /events` сам отдаёт активность владельца токена), событие пуша
   уже несёт заголовок коммита для одно-коммитных пушей (Compare API нужен только
   много-коммитным — меньше запросов, чем у GitHub), имя проекта приходится догружать
   отдельно по числовому id (с кэшем на прогон импорта), rate-limit — HTTP 429, а не 403.
   Привязка токена — `POST /api/me/gitlab-token`, тот же `TokenCipher`, отдельная таблица
   `gitlab_integrations` (V8) — **сознательно НЕ объединена** с `github_integrations` в общую
   схему, хотя более ранняя заметка в `docs/data-model.md` предлагала это сделать при
   появлении второго провайдера — обоснование отказа там же.
   Самостоятельное ревью нашло и закрыло реальный баг: `JsonElement.content` на JSON-`null`
   (не отсутствующем поле, а именно `null`) отдаёт строку `"null"` из четырёх символов, а не
   Kotlin `null` — фильтр `isNullOrBlank()` на `commit_from`/`commit_to` тихо пропускал бы
   такой мусор дальше, а `message ?: title`-фолбэк вообще не срабатывал бы. Исправлено на
   `contentOrNull` везде, где GitLab может явно прислать `null` (задокументированный случай
   "переполненных" пуш-событий). Отдельно нашёлся и более практический баг при первом прогоне
   полного набора тестов: добавление новой таблицы `gitlab_integrations` уронило 96 тестов
   ВО ВСЕХ существующих файлах (не только новых) — `toDto()` теперь читает обе таблицы
   токенов, а старые тестовые H2-схемы про новую ничего не знали; пришлось завести её в схему
   каждого файла, который регистрирует пользователя.
   Тесты: `GitlabTokenTest` (7) + `GitlabImportTest` (14, включая регрессию на JSON-`null`
   и оба вида rate-limit — на compare и на поиске имени проекта). Бэкенд — 157 тестов, зелёные.
   **НЕ проверено вживую** (в отличие от GitHub-импорта, сверенного через `gh auth token`) —
   токена GitLab для ручной проверки не было, форма API — по официальной документации,
   которая для GitHub уже расходилась с реальностью. Первая живая проверка — за пользователем.
   Android UI, как и у GitHub-импорта, пока нет.

Изменения из всех пунктов только закоммичены локально, **не задеплоены и не запушены**.

## Известные мелкие недочёты (найдено при живой проверке на телефоне, 2026-09-04)
**Оба закрыты 2026-10-10** (`ErrorMessages.kt`, `FeedScreen.kt` — NetworkCallback). Описание — для истории.

1. **Регистрация с коротким паролем не объясняет причину.** `LoginScreen.kt` — `catch (e:
   Exception)` на кнопке входа/регистрации всегда показывает один и тот же общий текст
   («Не удалось зарегистрироваться» / «Неверный email или пароль»), не различая реальную
   причину (короткий пароль сервер отклоняет отдельным сообщением, но клиент его не
   показывает). Похожая проблема шире: та же ловушка глушит и сетевые ошибки — именно
   из-за этого не сразу нашли причину ECONNREFUSED при первом локальном тесте с телефона.
   Чинить: разбирать `HttpException`/тело ответа (`ErrorResponse`) вместо одного текста
   на все случаи — как уже сделано в `ReportsViewModel.humanMessage()`.
2. **Автосинхронизация не срабатывает при восстановлении сети.** `EntryRepository.sync()`
   (в `shared/`) по своему же докстрингу должен вызываться «когда угодно: pull-to-refresh,
   восстановление сети, таймер» — но в `FeedViewModel.kt` (androidApp) реально вызывается
   только при открытии экрана, после add/edit/delete записи и один раз через 4с, если
   что-то «в обработке». Слушателя `ConnectivityManager` нет. Результат: запись, созданная
   офлайн, лежит в очереди и НЕ уезжает сама, когда интернет возвращается — нужно вручную
   нажать «Обновить» на ленте (кнопка есть, `FeedScreen.kt:83`) или заново отредактировать
   запись (это тоже дёргает `refresh()`), только тогда `sync()` реально отправляет очередь.
   Чинить: добавить `ConnectivityManager.NetworkCallback`, который сам зовёт `vm.refresh()`
   при появлении сети.

## Деплой / редеплой
- Файлы: `deploy/server/` (docker-compose + Caddyfile + Dockerfile'ы + README-runbook).
- Секреты на сервере (не в git): `.env` (DB_PASSWORD, DUCKDNS_TOKEN, DEVLOG_DOMAIN, DEVLOG_PORT),
  `devlog.env` (GROQ_API_KEY, JWT_SECRET, DEMO_REPORT_TOKEN). Домен — отдельный DuckDNS `vihreaschedule.duckdns.org`.
- Обновить бэкенд: `gradlew distTar` → `scp backend/build/distributions/devlog-backend-0.1.0.tar`
  в `/opt/devlog/backend/devlog-backend.tar` (`scp ... solmu-new:...`) → на сервере
  `docker compose up -d --build devlog-backend`. **Именно distTar, а не fat-jar:**
  в fat-jar склеиваются файлы `META-INF/services`, Flyway теряет плагины и МОЛЧА
  пропускает миграции — сервер поднимается с пустой базой.
- Caddy на сервере уже собран; пересобирать его не нужно. Если всё же придётся —
  версии в `caddy/Dockerfile` закреплены намеренно (Caddy 2.10 + duckdns v0.5.0).
