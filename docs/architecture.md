# DevLog — архитектура

## Общая модель
Клиент-сервер. **Сервер — единственный источник правды** (данные, бизнес-логика, ИИ).
Клиенты тонкие: показывают данные и шлют запросы. Так несколько клиентов (веб, Android,
iOS, десктоп) работают с одними данными и остаются согласованными.

```mermaid
flowchart LR
  subgraph Клиенты
    W[Веб-страница]
    A[Android]
    I[iOS]
    D[Desktop]
  end
  W & A & I & D -->|HTTPS REST + JWT| B[Бэкенд Ktor]
  B -.->|события SSE| W
  B --> DB[(PostgreSQL)]
  B -->|фоном| AI[Groq API]
  B -->|импорт| GH[GitHub API]
```

## Бэкенд
- **Ktor** — веб-фреймворк на Kotlin (уже знаком по Expenses).
- **PostgreSQL** — база данных; доступ через **Exposed** (Kotlin-обёртка над SQL) и
  **HikariCP** (пул соединений — переиспользует открытые подключения к БД).
- **REST API** — набор HTTP-«ручек» `/api/...` (перечень ниже). GraphQL пока не берём.
- **Схема БД** — миграции Flyway (`resources/db/migration/V…__.sql`), см. `data-model.md`.
- **Фоновая обработка ИИ:** запрос к ИИ идёт секунды, поэтому запись сохраняем сразу
  как «сырую» со статусом `queued`, а структурирование выполняет фоновый воркер.
  Клиент показывает «обрабатывается…», а о готовности узнаёт из события (см. ниже).

### Живые обновления вместо опроса (SSE)
Сначала браузер спрашивал сервер каждые 4 секунды: «уже готово?». Это лишние запросы
и задержка до нескольких секунд. Теперь клиент держит **одно открытое соединение**
(`GET /api/events`, механизм Server-Sent Events), и сервер сам присылает событие
`entry`, когда воркер дообработал запись. Поток односторонний (сервер → клиент),
поэтому WebSocket не нужен.

- События раздаёт `EntryEventBus` — по потоку на пользователя, **в памяти процесса**.
  Терять их не страшно: сама очередь обработки лежит в базе, а клиент при подключении
  всё равно перечитывает ленту. Если серверов станет несколько, сюда добавится общая
  шина (например, LISTEN/NOTIFY у PostgreSQL).
- **Токен для SSE — в cookie, а не в адресе.** Браузерный `EventSource` не умеет слать
  заголовок `Authorization`, а токен в адресной строке попал бы в логи прокси. Поэтому
  страница кладёт его в cookie `devlog_sse` с `path=/api/events` — она уходит только
  на эту ручку.
- Раз в 25 секунд сервер шлёт пустое событие `ping`: молчащие соединения рвут прокси.
- Если соединение не поднялось (старый браузер, прокси режет SSE), клиент возвращается
  к прежнему опросу раз в 4 секунды.

### Очередь обработки ИИ (AiWorker)
**Очередь хранится в базе, а не в памяти процесса.** Это ключевое решение: раньше сервер
запускал корутину «обработай запись» и забывал про неё, поэтому перезапуск сервера
(редеплой, падение) навсегда подвешивал записи в статусе `queued`/`processing`.

Как работает сейчас:
1. Запись сохраняется со статусом `queued` — это и есть «стоит в очереди».
2. `AiWorker` в цикле спрашивает базу: что не обработано? Берёт запись **атомарно** —
   помечает `processing` с условием «статус и число попыток всё ещё те, что я видел».
   Если условие не сошлось, запись успел забрать другой воркер, и мы просто берём следующую
   (заранее готово к нескольким инстансам сервера).
3. Успех → `structured`. Ошибка → текст ошибки в колонку `ai_error`, счётчик `ai_attempts`,
   возврат в очередь; после 3 неудач — окончательный `failed`, и пользователь **видит причину**.
4. Записи, застрявшие в `processing` дольше 5 минут, считаются оборванными (сервер
   перезапустили посреди обработки) и подбираются заново — по колонке `ai_started_at`.
5. Упёрлись в суточный лимит пользователя → запись возвращается в очередь без траты попытки,
   а пользователь до конца суток пропускается (иначе воркер крутился бы на нём вхолостую).

## Слой ИИ
- Провайдер — **Groq** (OpenAI-совместимый API, модель `openai/gpt-oss-120b`, запасная для отчётов — 20b); изначально
  планировался Claude API, заменён ради бесплатности на старте. Ключ хранится **только
  на сервере**, клиенты в ИИ напрямую не ходят (иначе ключ утечёт и любой сможет тратить
  деньги).
- **Структурированный вывод:** просим у модели строгий JSON по схеме (суть/шаги/решения/
  проблемы/итог/теги) через механизм «tool use», а не свободный текст — так результат
  надёжно кладётся в БД.
- **Контроль стоимости с первого дня:** лимит запросов на пользователя, батчинг (день
  пачкой), кэш. Модель структурирования и модель генерации отчёта можно выбрать разные.
- **Приватность:** явное предупреждение, что текст уходит в ИИ; выключатель ИИ на уровне
  проекта (`ai_enabled`); содержимое записей не пишем в открытые логи.

## Клиенты
- **Общий модуль `shared/`** — контракт API (все DTO) одним определением на бэкенд
  и Android. Раньше те же классы жили в трёх местах: сервер, приложение и JavaScript
  веб-страницы; достаточно было добавить поле на сервере и забыть про приложение, чтобы
  клиенты разъехались молча. Теперь несовпадение полей — ошибка компиляции, а не сюрприз
  в рантайме. `ApiContractTest` дополнительно стережёт **имена полей в JSON**: их видят
  уже установленные приложения, и переименование ломает старых клиентов.
  - Технически это обычная Kotlin-библиотека под JVM, а не KMP-модуль: её потребляют
    бэкенд (JVM 21) и Android (JVM 17), а iOS-таргета пока нет. DTO написаны на чистом
    Kotlin, поэтому превращение в KMP — правка одного build-файла, сами классы не меняются.
  - Подключается обоим сборкам через `includeBuild("../shared")`: отдельные Gradle-проекты
    остаются независимыми, публиковать модуль в репозиторий артефактов не нужно.
  - _Веб-страница на этот модуль не переведена: там чистый JS без сборки — осознанный выбор._
- **Android-приложение** — две вкладки: «Лента» (ввод записи, статус ИИ, структура) и
  «Отчёты» (сборка за период, просмотр готового документа, публичная ссылка).
  - Готовый HTML отчёта приходит **с сервера** (поле `contentHtml`) и показывается в WebView:
    конвертер Markdown живёт в одном месте, а не дублируется на каждом клиенте. JavaScript
    в WebView намеренно выключен — отчёт это текст, а выключенный JS убирает целый класс рисков.
  - Публичной ссылкой делимся системным «Поделиться»: сервер отдаёт относительный путь
    `/r/{token}`, адрес сервера подставляет приложение.
- **Kotlin Multiplatform (KMP)** — один код на Kotlin компилируется под Android/iOS/Desktop.
  **Compose Multiplatform** — тот же Jetpack Compose (знаком по SkyCast/DiceRoller), но
  работающий на всех трёх. UI пишется почти один раз.
- **Дальше в `shared/`:** сетевой слой (**Ktor Client**) и локальная БД
  (**SQLDelight** для офлайна) — когда дойдём до офлайн-режима.
- **Веб на старте — HTML-страница, которую отдаёт сам бэкенд** (как в Expenses).
  «Настоящий» веб на Compose/Wasm или отдельном фронтенде — позже (Wasm ещё сыроват).

## Данные, офлайн, синхронизация
- Сервер — источник правды (PostgreSQL). Клиенты кэшируют локально (SQLDelight).
- **Что изменилось после момента X:** `GET /api/entries/changes?since=…` отдаёт записи
  порциями. Клиент запоминает `serverTime` из ответа и в следующий раз присылает его
  как `since` — качать всю ленту заново не нужно.
  **`since`/`serverTime` — непрозрачная строка для клиента**, внутри — `sync_seq`:
  строго монотонный счётчик записи из БД-последовательности (`Entries.syncSeq`,
  `EntriesSyncSeq` в Tables.kt), а НЕ `updated_at` (timestamp). Прямой путь через
  `updated_at` пробовали дважды и оба раза он ломался: несколько записей МОГУТ получить
  одинаковый `updated_at` (быстрое создание подряд — например, импорт в цикле), и при
  строгом «`> since`» такая запись навсегда терялась бы между страницами; добавление
  `id` записи как тай-брейка тоже не помогло — случайный порядок UUID не совпадает
  с порядком вставки, и «более новая» запись могла оказаться «меньше» по id и выпасть
  из ответа. `sync_seq` устраняет проблему целиком: значения из последовательности
  никогда не повторяются и растут строго в порядке записи. Клиент не должен пытаться
  разобрать `since` как дату или число — только round-trip'ить как есть.
- **Мягкое удаление.** `DELETE` не стирает строку, а помечает её удалённой (`deleted_at`)
  и вычищает содержимое. Без этого устройство, которое было офлайн, не узнало бы об
  удалении и запись у него «воскресла» бы. В обычной ленте надгробий нет — только
  в синхронизации, с `deleted: true`.
- **Идемпотентное создание.** Клиент может прислать свой `id` (UUID) в `POST /api/entries`.
  Повторная отправка при плохой сети вернёт ту же запись, а не создаст дубль.
- Конфликты правок — «последняя запись побеждает» по `updated_at`.

## Авторизация и безопасность
- **JWT** (JSON Web Token — самодостаточный токен-пропуск): клиент логинится, получает
  токен, шлёт его в заголовке каждого запроса.
- Пароли — хеш (bcrypt/argon2), в открытом виде не храним.
- **Изоляция пользователей (multi-tenant):** каждый запрос ограничен `user_id` из токена;
  чужие данные недоступны в принципе. Ссылки на чужие сущности тоже проверяются:
  привязать запись или отчёт к **чужому проекту** нельзя (иначе можно было обойти его
  выключатель ИИ — для чужого проекта проверка «ИИ разрешён?» отвечала «да»).
- **Отказ старта с небезопасным секретом:** если `JWT_SECRET` не задан, сервер поднимется
  только на localhost. Слушать внешний адрес (в Docker `HOST=0.0.0.0`) с секретом
  из исходников он откажется — иначе кто угодно подписал бы себе токен с чужим `userId`.
- **Проверка входных данных:** кривая дата или id → `400` с понятным текстом, а не `500`.
  Длина заметки ограничена (`MAX_RAW_TEXT_LENGTH` = 20 000 символов) — защита базы
  и лимита обращений к ИИ от вставки на мегабайт.
- Публичная страница отчёта отдаётся с `noindex, nofollow` — секретная ссылка не должна
  попасть в поисковую выдачу.
- Рабочие данные конфиденциальны → выключатель ИИ по проектам, аккуратные логи, бэкапы `.gpg`.

## Контракт REST API (черновик Фазы 1)
Все `/api/*`, кроме auth и публичного просмотра отчёта, требуют JWT.

**Авторизация**
- `POST /api/auth/register` `{email, password, displayName}` → `{token}`
- `POST /api/auth/login` `{email, password}` → `{token}`
- `GET  /api/me` → `{id, email, displayName}`

**Записи**
- `GET    /api/entries?from=&to=&projectId=&q=&tag=` → список записей
  (`q` — поиск по сырому тексту и по структуре от ИИ; `tag` — точное совпадение тега)
- `GET    /api/entries/changes?since=&limit=` → `{entries, serverTime, hasMore}` —
  изменения для синхронизации, включая удалённые (`deleted: true`)
- `POST   /api/entries` `{projectId?, occurredOn, rawText, source?, timeSpentMin?, id?}`
  → запись (status=`queued`, ИИ обработает в фоне). `id` — необязательный UUID от клиента:
  повторная отправка с тем же id не создаст дубль
- `GET    /api/entries/{id}` → запись + структурированная часть
- `PUT    /api/entries/{id}` → правка сырого текста/метаданных
- `DELETE /api/entries/{id}` — мягкое удаление (остаётся надгробие для синхронизации)
- `POST   /api/entries/{id}/reprocess` → перезапустить ИИ

**Проекты**
- `GET/POST/PUT/DELETE /api/projects`

**Отчёты**
- `POST   /api/reports` `{projectId?, periodStart, periodEnd, format, template?, fromWeeklyReports?}` → отчёт
  (ИИ собирает). `template`: `default` — по темам; `employer` — «Отчёт работодателю»
  (`EmployerReport.kt`: Сделано / Проверено / Передано другим / Не сделано и почему, «Цифры»
  записей дня складываются кодом). `fromWeeklyReports: true` — месяц из уже вычитанных недельных
  отчётов того же проекта (дни без недельного отчёта — из записей); у проекта с выключенным ИИ
  недели склеиваются кодом и в Groq не уходят
- `GET    /api/reports`, `GET /api/reports/{id}` — в ответе и `contentMd`, и `contentHtml`
  (готовый HTML рендерит `Markdown.kt` — тот же код, что и публичная страница, без второго
  конвертера на клиенте)
- `PUT    /api/reports/{id}` `{contentMd, title?}` — правка перед отправкой работодателю
- `DELETE /api/reports/{id}`
- `POST   /api/reports/{id}/share` → `{shareToken, url}`
- `DELETE /api/reports/{id}/share` — отозвать публичную ссылку
- `GET    /r/{shareToken}` → публичная HTML-страница отчёта (без авторизации, `noindex`)

**События**
- `GET /api/events` → поток SSE. Токен — в cookie `devlog_sse`. События: `ready`
  (подключились), `entry` (`{entryId, status}` — запись изменилась), `ping` (сигнал жизни),
  `unauthorized` (токена нет или истёк — сервер закрывает поток).

**Статистика**
- `GET /api/stats/activity?from=&to=` → `{days, currentStreak, longestStreak, totalEntries,
  activeDays}` — данные для календаря активности за год и счётчика дней подряд

**Импорт**
- `POST /api/import/github` `{periodStart, periodEnd, projectId?, repo?}` →
  `{days, commits, created, updated, skipped, truncated}`. С `repo` ("владелец/имя" или ссылка) —
  режим «один репозиторий»: `GET /repos/{repo}/commits?author={login}&since&until`, до 10 страниц
  по 100, без лимита ~90 дней ленты, merge-коммиты пропускаются, период до 366 дней. В запись
  идёт заголовок **и описание** коммита (без `Co-Authored-By` и пр., до 600 символов) — при
  Conventional Commits первая строка бывает просто `feat(android)`. Без `repo` — прежний режим:
  тянет публичную активность GitHub
  (`/users/{login}/events/public`, без токена) и складывает коммиты каждого дня
  в одну запись дневника. Повторный импорт того же дня ничего не дублирует:
  id записи вычисляется из пользователя и даты; появились новые коммиты — запись дополняется,
  если её не правили руками (см. «Повторяемый импорт» ниже).
  Ограничения источника: только открытые репозитории, ~90 дней, до 300 событий.
- Логин GitHub хранится в профиле (`PUT /api/me {githubLogin}`); **токен не храним** —
  приватные репозитории потребуют его, и тогда появится отдельное хранилище секретов.
- `POST /api/import/text` `{text, projectId?}` → `{days, linesMatched, created, skipped}` —
  импорт произвольного текстового лога (см. решение ниже): текст режется на дни по датам
  ГГГГ-ММ-ДД, каждый день — отдельная запись дневника с тем же путём через ИИ-воркер.
  Повторный импорт того же куска текста не дублирует записи: id зависит от дня
  **и** содержимого (SHA-256 строк дня), а не только от дня, как у GitHub-импорта —
  иначе два РАЗНЫХ лога, случайно совпавших по календарному дню, затирали бы друг друга.
- `POST /api/import/gitlab` `{periodStart, periodEnd, projectId?}` →
  `{days, commits, created, skipped, truncated}` — тот же принцип ("коммиты дня → одна
  запись"), но токен ОБЯЗАТЕЛЕН (`POST /api/me/gitlab-token`): у GitLab Events API нет
  анонимного режима, поэтому и логина в профиле для него нет — `GET /events` сам
  возвращает активность владельца токена. Устроено внутри иначе, чем GitHub-импорт
  (GitLab отдаёт заголовок коммита прямо в событии для одно-коммитных пушей — Compare API
  нужен только многокоммитным), см. докстринг GitlabImport.kt за подробностями и явной
  пометкой, что форма API проверена по документации, а не вживую (в отличие от GitHub).

- `POST /api/import/day-files` `{files: [{name, text}], projectId?, overwrite?}` →
  `{created, updated, unchanged, failed, files: [{name, date, status, parsedByCode, message}]}` —
  импорт файлов дня (`ГГГГ-ММ-ДД.md` с разделами «Сделано», «Проверено», «Нехватки», «Не
  делалось», «Цифры»), до 100 за раз. Дата — из имени файла (иначе из заголовка `# …`:
  ГГГГ-ММ-ДД или ДД.ММ.ГГГГ), один файл — одна запись, id = пользователь + проект + день.
  **Разделы разбирает код** (`DayFileImport.kt`), запись сразу `structured`, ИИ не нужен —
  работает и у проекта с выключенным ИИ. Файл без «Сделано» идёт обычным путём (очередь/черновик).

**Токены для скриптов (`ImportTokens.kt`, V9).** `GET/POST /api/me/import-tokens {name}` →
`{token, info}` (токен — один раз), `DELETE /api/me/import-tokens/{id}`. Выдаются только под
обычным входом. Провайдер авторизации `import-token` (bearer) подключён ТОЛЬКО к
`/api/import/day-files` и `/api/import/text` — остальное с таким токеном отвечает 401.
В базе — SHA-256 токена. Клиент — `tools/push-day-files.mjs` (вручную, Планировщиком или
хуком Claude Code в режиме `--hook`), см. `docs/auto-import.md`.

**Повторяемый импорт (`ImportedEntries.kt`).** Файл дня дописывается в течение дня, за день
появляются коммиты — повторный импорт обычен. В `source_ref` записи импорт кладёт отпечаток
(SHA-256, 16 символов) текста, который записал сам. При повторе: текст тот же → `unchanged`;
отпечаток совпадает с текущим текстом (запись никто не трогал) → заменить, `updated`; не
совпадает → пользователь правил запись в DevLog → не трогать, `edited`. Удалённую запись
импорт не воскрешает (`deleted`). `overwrite: true` (только файлы дня) — заменить и то, и другое.

**Конфиденциальность в очереди ИИ.** Статус новой записи решает `EntryRepository.create` в той
же транзакции: у проекта с выключенным ИИ — сразу `draft`. Раньше запись рождалась `queued`, а
черновиком её делал вызывающий код — импорт GitHub/GitLab/текста этого не делал вовсе, и записи
конфиденциального проекта уходили в Groq. Последний рубеж — `AiWorker`: перед отправкой
проверяет выключатель проекта (его могли выключить, когда записи уже стояли в очереди).

**Экспорт (обратная сторона импорта)**
- `POST /api/reports/{id}/export-github` → `{repo, path}` — кладёт готовый отчёт (см. раздел
  «Отчёты») в один changelog-файл (по умолчанию `docs/devlog.md`) в репозитории пользователя
  через GitHub Contents API. Настройка — на проекте (`github_export_repo`/`github_export_path`
  в `Projects`, редактируются через `PUT /api/projects/{id}`), а не глобально: разные проекты
  могут экспортироваться в разные репозитории или не экспортироваться вовсе. Требует привязанный
  личный токен (тот же, что для импорта приватных репозиториев, — теперь ему нужны права на
  ЗАПИСЬ в целевой репозиторий). **Ручное действие по кнопке, не автоматика**: писать коммиты
  в чужую историю молча в фоне — не то, что делают без явного разрешения на каждый раз.
  Раздел отчёта в файле помечается HTML-комментарием `<!-- devlog:report:{id} -->`; повторный
  экспорт ТОГО ЖЕ отчёта (например, после правки текста) обновляет его раздел на месте вместо
  дублирования, разные отчёты — разные разделы, новый сверху. Подробности реализации и
  сознательные компромиссы — `GithubExporter.kt` и `docs/roadmap.md`, Фаза 4.

**Решение: импорт из Claude Code — общий текстовый парсер, а не разбор конкретного формата.**
Задача формулировалась как «импорт выгрузок Claude Code» (транскрипт сессии). У Claude Code
сессии действительно сохраняются локально построчным JSON (JSONL), но это **внутренний формат
для собственных нужд CLI**, нигде не задокументированный как стабильный публичный контракт
экспорта: нет гарантии, что поля/расположение файла не поменяются между версиями. Парсер,
завязанный на этот формат «на удачу», рисковал бы молча сломаться при следующем обновлении
CLI — а провал молча означает пропущенные дни дневника, что хуже, чем более скромная фича.
Вместо этого сделан **общий импорт произвольного текста с датами**: пользователь вставляет
что угодно текстовое (лог сессии, экспорт чата, скопированные заметки) — парсер ищет в каждой
строке подстроку `ГГГГ-ММ-ДД` и относит строку к дню последней встреченной даты. Это работает
для транскрипта Claude Code (у реплик обычно есть ISO-таймстемпы), но не только для него —
годится для любого текста с датами, что практичнее для портфолио-фичи. Обратная сторона:
без даты в тексте фича бессильна — сервер в этом случае отвечает 400 с понятным объяснением,
а не пытается угадывать структуру.

**Служебное**
- `GET /health` → `{"status":"ok"}` (открыта, для мониторинга и деплоя)
- `GET /api/config` → `{aiEnabled, aiDailyLimit}` — включён ли ИИ на сервере.
  Нужна интерфейсу: без ключа запись честно висит в очереди, и клиент пишет «ИИ выключен»,
  а не притворяется, что обработка идёт.
