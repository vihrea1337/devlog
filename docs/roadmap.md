      `EntryRepository.sync()` идёт по страницам since-протокола, upsert по id,
      `deleted: true` с сервера удаляет строку локально. `FeedViewModel` в androidApp
      переведён на этот путь вместо прямого `Retrofit.getEntries()`.
      Тесты: `EntryRepositorySyncTest` (`./gradlew :shared:test` из `backend/`) — первая
      синхронизация постранично, мягкое удаление, очистка кэша при выходе.
      **Не проверено вживую на телефоне** (только `assembleDebug` + JVM-тесты с
      in-memory SQLite и MockEngine вместо реальной сети).
- [x] Офлайн-**запись** (2026-09-02): `addEntry`/`deleteEntry` в androidApp больше не ждут
      сеть — `EntryRepository.enqueueCreate()`/`enqueueDelete()` пишут сразу в локальный
      кэш (таблица `entryEntity`) и ставят операцию в очередь `pendingOperation`
      (`db/PendingOperations.sq`). `sync()` теперь сначала отправляет очередь
      (`flushPending`), потом тянет `/changes` — так что применённый локально create
      не задваивается, когда since-протокол пришлёт ту же запись обратно (upsert по id).
      Отправка на сервер идёт через `DevLogSyncClient.createEntry()`/`deleteEntry()` (тот же
      Ktor-клиент). Ошибка отправки не роняет sync() — операция уходит на повтор
      с экспоненциальной задержкой (2с → 4с → 8с → 16с → 32с → потолок 60с),
      удаление уже отправленной/несуществующей записи (`404`) считается успехом.
      Если пользователь удаляет запись, пока её `create` ещё летит по сети (гонка,
      найдена и закрыта на самостоятельном ревью) — запись всё равно исчезает из ленты
      сразу, просто финальное удаление на сервере уедет следующим `sync()`, а не этим же.
      `reprocess()` офлайн-очередь сознательно не получил: это команда серверу
      "обработай ещё раз", а не изменение данных — без сети смысла в ней нет.
      Тесты: `EntryRepositoryPendingQueueTest` (8 тестов) — мгновенная видимость в кэше,
      успешная отправка create/delete, отмена ещё не отправленного create при удалении,
      идемпотентность 404 на delete, backoff (включая проверку, что повтор не уходит
      раньше срока), формула задержки, и отдельный тест на саму гонку выше.
      **Не проверено вживую на телефоне.**
      _Осталось на будущее:_ подлинный "last-write-wins" для конфликтующих правок
      (эта задача заводила только create/delete, не update — офлайн-редактирования
      текста записи пока не существует и на сервере, так что конфликтовать нечему).

## Фаза 4 — Киллер-фичи и SaaS-контур
- [x] **Импорт коммитов GitHub** (2026-08-12, доступ к приватным репозиториям — 2026-09-02):
      публичная активность → одна запись на день, дальше её разбирает ИИ; повторный импорт
      не дублирует. Без токена — публичная активность (как раньше); с личным токеном,
      привязанным в настройках (`POST /api/me/github-token`, зашифрован в БД —
      `github_integrations`, AES-GCM, ключ из JWT_SECRET, см. `TokenCipher.kt` и
      `docs/data-model.md`) — виден и приватный код. Тот же публичный endpoint GitHub
      Events API (`/users/{login}/events`), просто с заголовком Authorization — если токен
      принадлежит именно этому пользователю, GitHub сам отдаёт приватные события тоже.
      Токен нигде не логируется и не возвращается в ответах API — только факт привязки
      (`UserDto.githubTokenBound`). Веб-панель обновлена (поле токена + привязать/отвязать).
      Тесты: `GithubTokenTest` (8: шифрование/дешифровка, эхо токена в API, замена при
      повторной привязке, БД без открытого текста) + 2 новых в `GithubImportTest`
      (токен доезжает до fetchEvents / без токена уходит null).
      **Проверено реально** (не только моками): через `gh auth token` (аккаунт `vihrea1337`)
      привязал настоящий токен к тестовому локальному аккаунту devlog и прогнал импорт —
      подтверждено, что приватный репозиторий брата (`graywilson/moimatch`, виден только
      с токеном — сверено напрямую с GitHub API) действительно доступен через наш
      эндпоинт с токеном и недоступен без него; отдельно — заведомо неверный токен
      корректно даёт 502 с понятным текстом (значит, токен реально уходит в GitHub,
      а не тихо игнорируется). Токен нигде не сохранён после проверки (ни в файлах,
      ни в коммитах — только временная переменная окружения на время ручного теста).
      _Осталось: GitLab._
- [ ] ⚠️ **Найден баг, НЕ связанный с приватными репозиториями** (2026-09-02, при той же
      ручной E2E-проверке): у реальных `PushEvent` в GitHub Events API больше нет поля
      `payload.commits` — только `before`/`head` (SHA до и после пуша), без сообщений
      коммитов. Наш `parseCommitsByDay` эту форму не поддерживает и тихо не находит ни
      одного коммита ни в одном событии — из 37 реальных пушей за 90 дней распознано 0.
      Это ломает импорт GitHub **целиком, включая уже "готовую" публичную часть от
      2026-08-12** — вероятно, GitHub убрал `commits` из фида уже после того, как фича
      была написана и проверена только на синтетических тестовых данных. Юнит-тесты
      зелёные (они используют написанный вручную фикстур со старой формой ответа —
      реальность разошлась с тестом, а не с кодом). Чтобы получить реальные сообщения
      коммитов теперь, видимо, нужен отдельный запрос на репозиторий/пуш (например,
      сравнение `before...head` через compare API или `GET /repos/{owner}/{repo}/commits`) —
      это отдельная, более крупная переделка (N+1 запросов на событие, лимиты запросов),
      не делалась в рамках этой задачи (она была про доступ к приватным репо, а не про
      формат ответа). **Приоритет: высокий** — без этого фикса импорт GitHub бесполезен
      в реальности, несмотря на зелёные тесты.
- [x] **Импорт текстового лога, в т.ч. выгрузок Claude Code** (2026-09-02): тот же паттерн,
      что у импорта GitHub («внешний источник → одна запись на день → существующий
      ИИ-воркер разбирает»), но источник — произвольный вставленный текст, а не GitHub API.
      **Архитектурное решение** (полное обоснование — `docs/architecture.md`, раздел
      «Решение: импорт из Claude Code»): у сессий Claude Code нет стабильного
      задокументированного формата экспорта, поэтому вместо разбора конкретного JSONL
      сделан **общий парсер** — режет текст на дни по датам ГГГГ-ММ-ДД, встреченным
      в строках. Работает для транскрипта Claude Code (у реплик обычно есть
      ISO-таймстемпы), но и для любого другого текста с датами — практичнее узкого решения.
      `POST /api/import/text {text, projectId?}`, панель на веб-странице рядом с GitHub
      (в Android UI, как и у GitHub-импорта, пока нет). Дедуп — по дню **и** содержимому
      (SHA-256 строк дня, не только дата): повторная вставка того же текста не дублирует,
      а другой лог, случайно попавший на тот же день, ложится отдельной записью, а не
      затирает предыдущую (иначе, в отличие от GitHub-импорта, было бы легко потерять
      данные — источник тут не один и тот же по смыслу при каждом запросе).
      Тесты: `TextImportTest` (9 тестов) — разбиение на дни, невалидные даты, дедуп по
      контенту, HTTP-сценарии (создание, повтор, разные логи за один день, текст без дат).
      Прогнано вручную end-to-end через реальный HTTP (не только тесты): запустил бэкенд
      локально, зарегистрировал пользователя, импортировал текст с двумя днями — обе
      записи создались с `source: "text-import"`.
      **Не проверено:** реальная выгрузка настоящей сессии Claude Code (проверялось только
      на синтетических примерах с явными датами); UI не открывался в браузере вручную,
      только смок-тест `curl`/`Invoke-RestMethod` на сам API.
